# Database scripts

Supported versions:
- **PostgreSQL 16 or later.** Verified on 16.15.
- **pgvector 0.8 or later.** Verified on 0.8.1; iterative HNSW scans need 0.8.
- Contrib extensions `pg_trgm`, `pgcrypto` and `citext`.

## Layout

| Path | Content |
|---|---|
| `migrations/01_extensions.sql` to `migrations/14_seed_reference.sql` | **Source of truth.** Ordered, idempotent SQL. Alembic revisions `0001` to `0014` in `backend/alembic/versions/` each execute one file |
| `extensions.sql` | Bundle: 01 |
| `roles.sql` | Bundle: 02. Roles and cluster-level settings, with `{{…_PASSWORD}}` placeholders |
| `schema.sql` | Bundle: 03–06. Platform/tenant, identity and access, documents, chunks and embeddings tables; RLS helper functions; `app.refresh_document_acl` |
| `rls_policies.sql` | Bundle: 07. Restrictive tenant policies, permissive per-mode and ACL policies, grants |
| `indexes.sql` | Bundle: 08. HNSW (per dimension), GIN (FTS, trigram, ACL arrays), B-tree and BRIN |
| `domain_tables_and_policies.sql` | Bundle: 09–12. Chat, AI configuration, audit and analytics, evaluation tables, each with its own RLS and grants |
| `functions.sql` | Bundle: 13. SECURITY DEFINER authentication functions |
| `seed_data.sql` | Bundle: 14. Reference data only: plans, platform roles and permissions, the tenant permission catalogue, the local AI provider and model catalogue, default platform settings. **No users and no tenant data** |

The bundles are generated by `python scripts/build_sql_bundle.py`; edit the migration files, not the bundles. Each bundle runs in a single transaction (`BEGIN`/`COMMIT`), because the seed uses transaction-local `set_config`.

## Recommended installation (automated)

```bash
cd backend
python -m app.database.bootstrap      # superuser (DB_SUPERUSER_DSN): roles + passwords, database, extensions
alembic upgrade head                  # as rag_migration: 0001..0014
```

Or run `scripts/migrate.sh` (Linux/macOS) or `scripts/migrate.ps1` (Windows).

Both steps are idempotent. The bootstrap:
1. creates or updates the roles;
2. sets their passwords from `DB_*_PASSWORD`, substituted as quoted literals;
3. re-asserts `NOSUPERUSER NOBYPASSRLS`;
4. creates the database owned by `rag_migration`, plus the extensions.

`--drop-existing` recreates the database. It is for development and tests only and is refused when `ENVIRONMENT=production`.

## Manual installation with psql

Use this when Python is not available on the database host.

```bash
# 1. as a superuser: roles (substitute real passwords from your secret store first)
sed -e "s/{{RAG_MIGRATION_PASSWORD}}/'<pw1>'/" -e "s/{{RAG_APP_PASSWORD}}/'<pw2>'/" \
    -e "s/{{RAG_WORKER_PASSWORD}}/'<pw3>'/" -e "s/{{RAG_READONLY_PASSWORD}}/'<pw4>'/" roles.sql > /tmp/roles.sql
psql -U postgres -v ON_ERROR_STOP=1 -f /tmp/roles.sql && rm /tmp/roles.sql
createdb -U postgres -O rag_migration enterprise_rag
psql -U postgres -d enterprise_rag -v ON_ERROR_STOP=1 -f extensions.sql

# 2. as rag_migration, in this order
for f in schema.sql rls_policies.sql indexes.sql domain_tables_and_policies.sql functions.sql seed_data.sql; do
  psql -U rag_migration -d enterprise_rag -v ON_ERROR_STOP=1 -f "$f"
done

# 3. tell Alembic the schema is at head, so future upgrades apply cleanly
cd ../backend && alembic stamp head
```

A manual install into an empty database was verified: 67 tables and 223 policies.

## Verifying a database

```sql
-- no service role may bypass RLS
SELECT rolname, rolsuper, rolbypassrls FROM pg_roles WHERE rolname LIKE 'rag_%';
-- every application table has RLS enabled AND forced (expected: only iam.permissions is listed)
SELECT n.nspname || '.' || c.relname FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
 WHERE c.relkind = 'r' AND n.nspname IN ('platform','iam','content','ingest','rag','ai','eval','audit','ops')
   AND NOT (c.relrowsecurity AND c.relforcerowsecurity);
-- policy count
SELECT count(*) FROM pg_policies;
```

The automated proof is `backend/tests/rls/test_rls_isolation.py`. It connects as `rag_app` and `rag_worker`, never as a superuser.

## Writing new migrations

1. Add `database/migrations/15_<name>.sql`, idempotent: `IF NOT EXISTS`, `CREATE OR REPLACE`, `DROP POLICY IF EXISTS`.
2. For every new tenant-owned table:
   - add `tenant_id uuid NOT NULL`;
   - add `UNIQUE (tenant_id, <pk>)` if other tables will reference it;
   - add composite foreign keys;
   - call `SELECT app_admin.apply_tenant_rls('<schema>.<table>')`;
   - add the permissive policies for each access mode that needs the table;
   - grant only the required privileges to `rag_app`, `rag_worker` and `rag_readonly`.
3. Add `backend/alembic/versions/0015_<name>.py` calling `run_sql_file("15_<name>.sql")`, then run `python scripts/build_sql_bundle.py` and `python scripts/generate_db_docs.py`.
4. Never grant `BYPASSRLS`. Never add a policy for the `platform` mode on tenant content tables.
